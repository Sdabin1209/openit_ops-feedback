# 영역 브리프: 운영 관측·피드백 (ops-feedback)

> **계약 상태.** 영역 사이 계약은 `../boundary-contracts`(헤드 소유)에 있고, 이 브리프의 계약 이름은 `head/docs/STRUCTURE.md`의 제안이다. 초안이 있는 것은 ReleaseManifest, GateDecision, TraceEnvelope뿐이고 나머지 필드는 헤드가 사용자와 논의해 확정 중이다. 확정 전에는 **계약에 의존하지 않는 부분**(내부 설계, 도메인 모델, 테스트 틀)만 진행한다. 계약이 부족하다고 느끼면 임의로 가정하지 말고 `docs/change-requests/`에 쓴다.
> **읽기.** `../boundary-contracts`와 `../survey-service/schema`는 문진 서비스의 데이터 스키마(스키마만 남긴 최소 구성)다. 구현이 가져가는 계약은 `schemas/<계약명>.json`(JSON Schema Draft 2020-12), 컴포넌트별 입력·출력 대응은 `COMPONENTS.yaml`, 정수 버전은 `CONTRACT_VERSION`이다. 둘 다 읽기 전용이다.
> **버전(D14, D19).** 문진 스키마는 정수 버전(`CONTRACT_VERSION`, 현재 1)에 정확히 일치해야 한다. 경계 계약은 `MAJOR.MINOR`이며 값은 `boundary-contracts`가 정한다. 불변 산출물은 `ArtifactRef`(id, version, content_hash)로 가리킨다.

## 1. 목적과 범위

- 목적: 운영 중 기록을 받아 비식별하고, 실패 사례를 가려내 다른 영역의 입력으로 돌려준다.
- 하는 일: 로그 수집, 비식별 처리, 실패 탐지, 사례 분류, 사람 검토 큐, 지표 대시보드, 피드백 배포, 롤백 요청.
- 하지 않는 일: 롤백을 직접 수행하지 않는다(게이트에 요청). 실패의 원인 수정은 하지 않는다.

## 2. 소유하는 것

- 소유 저장소: 로그 저장소(원본), 실패 사례 저장소.
- 제공하는 SDK 인터페이스: 로그 수집 SDK(문진 서비스가 `TurnTrace`·`LogEntry`를 보냄), 실패 사례 게시 SDK, 실패 사례 읽기 SDK(합성 데이터, model-lab, 문항 저작이 소비).
- 제공하는 서비스 API: ingest-api(수집). 같은 턴 ID로 다시 받아도 결과가 같아야 한다.
- 이 SDK의 메모리 구현(가짜 구현)을 함께 배포한다.
- 생산하는 계약: `FailureCase`, `RollbackRequest`.

## 3. 소비하는 것

- 소비하는 계약: `TraceEnvelope`, `TurnTrace`, `ReleaseManifest`, `GateDecision`.
- 소비하는 SDK: 릴리스 읽기 SDK(release-gate), 롤백 요청 API(release-gate). 라이브러리로 문진 스키마.
- 지원하는 계약 버전: 문진 스키마 정수 버전(Trace에 적힌 버전 여러 개를 읽을 수 있어야 한다), 경계 계약 `MAJOR.MINOR`.

## 3-1. 경계 명세 (블랙박스 기준)

상대 영역은 블랙박스다. 아래 인터페이스 번호의 시그니처, 오류, 멱등성은 `../boundary-contracts/INTERFACES.md`와 `CONVENTIONS.md`가 정한다. 이 명세 밖의 것을 상대에게 기대하거나 가정하지 않는다.

- 내는 것: **I6** TraceIngest(수집), **I7** FailureStore.
- 받는 것: **I6** `TraceEnvelope`(서비스가 보냄), **I4**(릴리스 정보), I5 `request_rollback` 호출.
- 해야 하는 것: (session_id, turn_id)로 중복을 제거한다. 원본은 비식별 처리기만 읽는다. `FailureCase`에는 비식별을 마친 것만 넣고, 검토 결과는 `version`을 올려 새로 게시한다. 롤백 요청에는 근거 지표 참조를 담는다.

## 4. 상위 수용 기준

- 로그 저장소의 원본은 비식별 처리기만 읽는다. 대시보드·검토 큐·실패 사례 저장소에는 비식별 뒤의 데이터만 간다.
- `FailureCase`에 비식별 전 데이터가 들어가지 않는다.
- 수집은 멱등이다. 중복 전달이 Trace 중복을 만들지 않는다.
- 모든 실패 사례에 출처 릴리스 ID가 있다.
- 롤백 요청에는 현재·되돌릴 릴리스 ID와 근거 지표 참조가 있다.

## 5. 비기능 요구

- 지연: 수집은 서비스의 턴 처리를 막지 않는다. 가용성: 수집 장애가 문진 서비스를 멈추지 않는다.
- 자원: 일반 CPU 서비스와 저장소 용량.
- 보안·개인정보: 이 영역이 개인정보의 경계다. 비식별 기준과 보관 기간은 미정이며 사용자가 정한다.

## 6. 건드리면 안 되는 경계

- 로그 저장소와 실패 사례 저장소에 쓰는 영역은 이 영역뿐이다.
- 롤백은 요청만 한다. 활성 포인터는 게이트만 바꾼다.

## 7. 이 영역에 해당하는 열린 결정

- O03 비식별 처리의 위치: 확정: 이 영역 안의 비식별 처리기, FailureCase는 항상 비식별 뒤에만 생성(D15).
- O04 Trace 내보내기의 전달 보장: 확정: 최소 1회 전달과 턴 ID 멱등(D16).
- O16 허용 중단 시간과 복구 시점: 사용자 결정.
- O10 저장소의 실제 기술: 영역이 정한다.

## 8. 시드

로그 수집기, 비식별 처리기, 실패 탐지기, 사례 분류기, 사람 검토 큐, 지표 대시보드, 피드백 배포기.
