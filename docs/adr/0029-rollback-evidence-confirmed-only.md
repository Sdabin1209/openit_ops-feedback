# 0029. 롤백 요청의 근거는 사람이 CONFIRMED로 검토한 사례만 센다

- 상태: 채택(L07, FAULT 시나리오 S5). 0006을 보강한다.
- 맥락: 수집 토큰만 있으면 임의 Trace를 넣을 수 있다(CR-006). 이전에는 설정 `rollback.counted_review_statuses`에 PENDING을 넣을 수 있었고(예시 설정과 시험이 그렇게 썼다), 잡은 자동 탐지가 만든 PENDING 사례를 실패로 세어 실패율을 올렸다. 위조 Trace 여러 건이면 사람이 보지 않고도 롤백 요청이 만들어지고 `auto_submit: true`이면 게이트까지 갔다.
- 결정: 롤백 평가는 `review_status == CONFIRMED`인 사례만 센다. 설정에서 이를 강제한다: 계약 `OpsFeedbackJobConfig`는 상태 이름을 문자열로만 받으므로 영역 스키마 `JobConfigChecks`(시작 때 거부)와 `RollbackAssessRequest.policy`(판단 컴포넌트 입구)가 `counted_review_statuses`의 모든 항목을 `CONFIRMED`로 제한한다.
- 왜: 환자 안전에 닿는 조치의 근거는 사람이 확인해야 한다는 0006(D88/U11)의 같은 원칙을 요청 생성 단계까지 내린 것이다. 신뢰 경계(수집 토큰)가 사람 검토 앞에 있기 때문에, 탐지의 정확도를 높이는 방법으로는 위조를 막을 수 없다.
- 검토한 대안과 버리는 이유: (1) `auto_submit`만 false로 둠 -> 요청 기록과 지표 스냅샷은 여전히 위조로 쌓이고 사람이 위조된 요청을 승인할 수 있다. (2) Trace 서명/출처 인증 -> 계약 변경이 필요한 별도 일(CR-006). 이 결정은 그것을 막지 않고 둘 다 있어도 된다. (3) 설정 값으로 PENDING을 허용 -> 설정 오류 하나로 다시 위조에 열린다.
- 결과: 얻는 것은 사람 검토 없이는 롤백 요청이 나가지 않는다는 구조적 보장. 감수하는 것은 검토 지연만큼 롤백 요청이 늦어지는 것(나쁜 릴리스 감지가 사람 검토 속도에 묶인다)과, 사람이 위조 사례를 확정하면 여전히 근거가 된다는 점. 분모(총 턴 수)는 원본 건수라 위조 Trace가 분모를 키워 실패율을 낮출 수는 있다(막지 않았다).
- 되돌리는 조건: Trace 출처 인증이 계약에 들어가 수집 입구에서 위조가 막히고 사용자가 자동 탐지 근거를 허용하기로 정할 때.
