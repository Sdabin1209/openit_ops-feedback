# 0004. 비식별은 허용 목록 방식, 필드별 처리와 값 검증

- 상태: 채택(O03/D15). 값 검증은 2026-10-28 추가.
- 맥락: Trace에는 발화 원문, 환자 답변, 모델 출력 문자열, 직원 ID가 섞여 있다. 사례에는 개인정보가 없어야 한다.
- 결정: 문진 스키마(TurnTrace)를 따라 걸으며 허용한 것만 남긴다(`deid.py`). 스키마가 열거·상수로 정한 문자열은 남기고, 자유 문자열은 정책이 키로 허용한 것만 남기고 나머지는 `[MASKED]`. 스키마에 없는 키와 구조 없는 자유 객체는 제거. 정책이 지목한 정의(`Value`)는 통째로 마스킹. 마지막에 잔존 패턴(이메일·전화·주민번호) 검사, 걸리면 `DeidError`로 닫는다. 남기는 키(`question_id, slot_id, repeat_key, code, path, action, next_item`)는 값이 식별자 모양(전체 일치 정규식, `deid.DEFAULT_KEEP_PATTERNS`)일 때만 남기고 아니면 마스킹한다. `session_id`, `turn_id`는 salt 해시(`p-`+32자)로 치환한다.
- 왜: 허용 목록(default deny)은 개인정보 보호의 표준 설계 원칙(fail-closed)이다. 새 필드가 생겨도 기본이 "지움"이다. 값 검증을 더한 이유는 실측이다: 점검에서 `next_item="홍길동 환자"`가 그대로 남았다(head/docs/audit/ops-feedback.md S1).
- 패턴 값의 근거: 문항 ID가 `Q1`, `Q2_1` 같은 모양이라는 것은 시험 데이터와 survey-service 스키마 예시에서 본 것이다. 스키마 자체는 `QuestionId`를 `minLength 1` 문자열로만 정한다. 따라서 패턴 길이 한도(64 등)는 **근거 기록 없음, 보수적 임의값**이고 설정(`deid.keep_string_patterns`)으로 바꾼다.
- 대안: 차단 목록(알려진 개인정보 패턴을 지우기) -> 한국어 이름·주소는 정규식으로 못 잡고 목록에 없는 것은 통과한다. 의료 도메인에서 권하지 않는다고 O19 권고도 적고 있다. 모델 기반 비식별 -> 재현성(같은 입력에 같은 결과)과 설명 가능성이 떨어진다. 둘 다 버린다.
- 결과: 얻는 것은 새 필드에 안전한 기본값. 감수하는 것은 유용한 문자열도 마스킹된다는 점(발화 문장이 `[MASKED]`)과, 식별자 모양의 영문 이름은 못 거른다는 한계. 검토자가 직접 쓰는 `expected`·`reviewed_input`은 비식별기를 거치지 않으므로 이메일·전화·주민번호 패턴이 있으면 거부한다(이름은 사람 책임).
- 되돌리는 조건: O19(비식별 뒤 발화 문장 보존 범위)가 B/C로 바뀌면 정책을 개정한다.

## 추가 2026-10-29: 주민등록번호 모양 패턴을 외국인등록번호까지 넓힘 (표준성 점검 B7)
- 결정: `rrn_kr`(예시 설정의 잔존 패턴과 검토 입력 기본 패턴)의 뒷자리 첫째 숫자를 `[1-4]`에서 `[1-8]`로 넓힌다. 5~8은 외국인등록번호에 쓰이는 것으로 확인했다(1900년대 출생 남·여 5·6, 2000년대 7·8).
- 확인한 정도: 뉴스 기사 한 건과 개인 글 여러 건으로만 확인했다. 법령·법무부 원문은 **확인 못 함**. 1800년대 출생 내국인(9, 0)은 이 패턴에 넣지 않았다.
- 한계: 패턴은 모양 검사이고 체크섬·생년월일 유효성은 보지 않는다. 6자리 뒤 1~8로 시작하는 7자리 숫자열은 모두 걸리므로 오탐이 늘 수 있다(측정 안 함). 오탐은 `DEID_FAILED`로 닫히는 쪽이다.
- 시험: `tests/test_rrn_pattern.py`.
