# 0001. 개발·시험은 SQLite, 운영은 PostgreSQL

- 상태: 채택(운영 PostgreSQL은 사용자 결정, 커밋 25dd29f). 시점: 2026-10.
- 맥락: 로그 저장소와 실패 사례 저장소가 필요하다. 처음에는 SQLite 파일 두 개로 구현했다(커밋 ee0715d). 운영에서는 서버와 잡이 같은 저장소를 동시에 쓰고, 백업·복구와 계정 권한 분리가 필요하다.
- 결정: 두 저장소를 인터페이스(`_RawBackend`, `_Backend`) 뒤에 두고 구현을 셋 둔다: 메모리, SQLite, PostgreSQL. `OPS_*_DATABASE_URL`이 있으면 PostgreSQL, 없으면 SQLite 파일. 같은 적합성 시험(`tests/test_conformance_*.py`)을 세 구현이 통과한다.
- 왜:
  - 운영 PostgreSQL: docs/design.md 2절이 이유를 적고 있다 "다중 프로세스 동시 쓰기, 백업·복구, 계정 권한 분리가 표준 도구로 해결된다(사용자 결정)". 표준 근거는 서버형 RDBMS의 일반 운영 관행이다. 특정 문헌·벤치마크는 적혀 있지 않다(근거 기록 없음).
  - 개발·시험 SQLite: 표준 라이브러리(`sqlite3`)라 외부 서버 없이 시험이 돈다. D22(개발은 컨테이너 밖에서, 이웃은 메모리 구현으로 혼자 시험)와 맞다.
- 검토한 대안:
  - 운영도 SQLite 파일: 서버와 잡이 같은 볼륨의 WAL 파일을 공유해야 하고, 계정 단위 권한 분리와 표준 백업 도구가 없다(design.md 2절의 이유). 그래서 버린다.
  - 메모리만: 재시작하면 사라져 운영 불가.
- 결과: 얻는 것은 세 구현의 동일 의미를 시험이 보장하는 것. 감수하는 것은 SQL 방언이 둘(`?`/`%s`)이라 문장을 두 번 쓰는 것, PostgreSQL 시험은 서버가 있어야 돈다(`scripts/dev-postgres.sh`).
- 되돌리는 조건: 단일 프로세스·단일 호스트로 충분하고 PostgreSQL 운영 부담이 이득보다 커지면 SQLite를 운영으로 재검토. 복제·고가용성은 O16(허용 중단 시간) 결정 뒤.
