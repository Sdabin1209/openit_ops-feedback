# 0016. 의사 식별자는 HMAC-SHA256(키=salt)

- 상태: 채택(헤드 결정, 표준성 점검 2026-10-29 B4 = `docs/audit/standards-2026-10-29.md`). 0004의 "salt 해시(`p-`+32자)"를 구체화하고 식을 바꾼다. 원문 대조: 아래 표준 이름과 요구는 이 영역이 원문을 다시 열어 확인하지 않았다(헤드 결정서에 "원문 대조" 표시).
- 맥락: 이전 식은 `SHA-256(JCS({salt, key, value}))`의 앞 128비트였다. 키 있는 해시를 직접 구성한 것이고 표준 HMAC과 비교한 기록이 없었다.
- 결정: `deid.pseudonym_of` 한 함수에서만 `HMAC-SHA256(키=salt의 UTF-8, 메시지=JCS({key, value}))`의 앞 32 hex(128비트)에 `p-`를 붙인다. 비식별 처리기와 `admin delete-session`이 같은 함수를 쓰는 구조(OF-03)는 그대로다. 출력 형식 `p-`+32 hex를 유지하므로 `FailureCase`·trace 스키마와 `_PSEUDONYM` 패턴은 바뀌지 않는다.
- 왜: 키 있는 해시(메시지 인증 코드)의 표준 구성은 HMAC이다(RFC 2104, FIPS 198-1). 비밀을 메시지 앞에 붙인 해시는 구성 방식이 표준이 아니고 해시 함수의 성질에 기대는 점을 따로 따져야 한다. HMAC은 그 따짐이 필요 없다. NIST SP 800-107도 HMAC을 키 있는 해시로 다룬다(원문 대조 전). 파이썬 표준 `hmac`을 쓰므로 직접 만든 암호 구성이 없다.
- 절단: 앞 128비트만 쓴다. HMAC 출력 절단은 RFC 2104가 허용하는 방식으로 알고 있다(원문 대조 전). 128비트로 한 이유는 기존 형식과 스키마 패턴을 유지하기 위해서다. 충돌 확률이나 사전 공격 비용은 계산하거나 측정하지 않았다.
- 대안: (a) 이전 식 유지: 표준이 아니고 근거가 없다. (b) HMAC 전체 256비트 출력: 스키마·형식이 바뀌어 계약 변경이 필요하다. (c) HKDF나 Argon2 같은 키 확장: 입력(session_id, turn_id)이 낮은 엔트로피 비밀번호가 아니라 서비스가 만든 ID이고, 비밀은 salt(키)라서 지금은 필요하다고 판단하지 않았다. 이 판단은 측정하지 않았다.
- 결과: 얻는 것은 표준 구성과 독립 계산으로 검증되는 기대값(`tests/test_pseudonym_hmac.py`는 표준 `hmac`으로 따로 계산한 값과 비교). 감수하는 것: **같은 salt와 입력에서도 의사 식별자가 바뀐다.** 이 변경 전에 만든 비식별 trace·사례의 `p-…`와 `case_id`(`fc-…`은 의사 식별자에서 파생), `admin delete-session`이 찾는 값이 새 식과 다르다. 이미 사례가 쌓인 배포는 새 식으로 다시 가명화하는 절차가 필요하다(salt 회전과 같은 절차, ADR 0017). 기존 배포 유무와 데이터 양은 이 영역이 확인하지 못했다. 예시 파일(`examples/output.*.json`)은 다시 생성했다.
- 되돌리는 조건: 계약이 의사 식별자 형식을 바꾸거나(256비트 등) 표준 문서 대조에서 위 이해가 틀렸음이 드러나면 새 ADR로 대체한다.
