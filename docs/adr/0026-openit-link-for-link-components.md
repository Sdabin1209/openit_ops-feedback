# 0026. 받는 쪽 통신 컴포넌트는 openit_link 위에 쓴다

- 상태: 채택(U400 추가 지시, D118). [0020](0020-wsgi-waitress.md)의 "세 면이 한 WSGI 앱" 결정을 이어받아, 앱의 인증·상한·검증·오류 본문 규약을 공유 라이브러리로 넘긴다.
- 맥락: `api.py`가 토큰 -> 역할(401/403), 본문 상한, 계약 검증, `BoundaryError` 본문, `/healthz`를 직접 구현했다. 같은 규약을 영역마다 따로 구현하면 어긋난다.
- 결정: `components/link_ingest_api.py`는 `openit_link.App/Route`로 경로 표(5개)만 적는다. 토큰은 면별 접두 역할(`ingest`, `read:<역할>`, `review:<역할>`)로 표에 넣는다. 영역이 남기는 것: 쿼리 문자열 검증(`ListCasesQuery`는 영역 스키마라 라이브러리의 계약 스키마 검증으로 못 한다), `/readyz` 본문과 프로세스 계수(응답 상태를 보고 센다), 서버 종료 손잡이(waitress). 보내는 쪽은 계약 클라이언트를 `link_release_read`·`link_gate_send`가 감싼다.
- 왜: 규약의 정본은 계약 CONVENTIONS 6·9절이고 한 곳(link)에서 지키는 편이 일관된다.
- 달라진 동작(시험으로 고정): 큰 본문은 400 대신 413, 허용하지 않는 메서드는 404 대신 405, 토큰 비교는 라이브러리의 상수 시간 비교(v0.2.0). 깊게 중첩된 JSON은 라이브러리가 500을 낸다([CR-010](../change-requests/CR-010-link-recursion-error.md), 시험 xfail).
- 검토한 대안: 기존 구현 유지(규약이 영역마다 달라진다).
- 결과: 얻는 것은 규약 코드 제거(약 200줄). 감수하는 것은 라이브러리 버전 고정(`requirements.txt`의 태그)과 위 동작 변화.
- 되돌리는 조건: 라이브러리가 이 영역의 면(역할 3종, 쿼리 검증)을 표현하지 못하게 되면 변경 요청으로 라이브러리에 올린다.
