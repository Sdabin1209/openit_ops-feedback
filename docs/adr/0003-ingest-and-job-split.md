# 0003. 수집 서버(ingest)와 주기 잡(job)을 나눈다

- 상태: 채택(D39, 브리프 4절·5절).
- 맥락: 수집은 문진 서비스의 턴을 막으면 안 된다(브리프 5절). 비식별·탐지·분류·롤백 평가는 오래 걸릴 수 있고 같은 입력에 같은 결과여야 한다.
- 결정: ingest-api는 받아서 원본을 쌓기만 하고(`POST /v1/traces`), 비식별 이하는 `job` 명령이 한 번 실행한다. 실행 시점은 deploy 스케줄러가 정한다(D39 "영역은 스스로 다른 영역을 깨우지 않는다").
- 왜: D39(저장소를 보고 일하는 멱등 잡)을 따른다. 수집 경로를 짧게 해 지연과 장애 전파를 줄이는 것은 일반적인 큐-워커 분리 원칙이다.
- 대안: 수집 때 동기로 비식별까지 -> 비식별 실패·지연이 문진 서비스 재전송으로 번진다. 상시 워커 프로세스 -> 스케줄은 deploy 소유라는 D39와 어긋난다.
- 결과: 얻는 것은 수집 지연 최소와 재실행 안전. 감수하는 것은 사례가 잡 주기만큼 늦는다는 점. 처리량·주기는 측정 안 함.
- 되돌리는 조건: 사례 지연이 소비자에게 문제가 되면 주기 단축부터, 그래도 안 되면 상시 워커 검토.
