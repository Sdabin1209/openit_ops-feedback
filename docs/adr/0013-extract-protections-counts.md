# 0013. extract_protections의 규칙 코드별 건수는 식별자 모양 키와 정수만 남긴다

- 상태: 채택(헤드 위임 G14, 2026-10-28). 0004의 "구조 없는 자유 객체는 제거"에 대한 예외를 설정 선택으로 더한다.
- 맥락: `extract_protections`는 스키마(`Protections`)에서 키가 자유 문자열이고 값이 0 이상 정수인 맵이다("규칙 코드별 건수", boundary-contracts HTTP.md의 `X-Openit-Protections: G5:1,G2:2`). 지금까지 자유 객체라 통째로 비워졌다. 건수는 모델 출력이 어떤 보호 규칙에 걸렸는지 알려 실패 사례 분석에 쓸모가 있다.
- 결정: 설정 `deid.keep_count_map_keys`에 적힌 필드(예시 설정은 `extract_protections`)만, 스키마가 값을 정수로 정한 맵일 때, 키가 `[A-Z][A-Z0-9_]{0,31}`(설정 `deid.count_map_key_pattern`)에 전체 일치하고 값이 0 이상 정수(불리언 제외)인 항목만 남긴다. 나머지 항목은 기록 없이 버린다. 설정에 없으면 이전처럼 비운다. `response_protections`는 같은 형태지만 이번 결정 범위가 아니라 비운 채로 둔다.
- 왜: 개인정보 최소 수집 원칙은 목적에 필요한 것만 남기는 것이다. 정수 건수는 그 자체로 식별정보가 아니다. 위험은 키다: 스키마가 키를 열거하지 않아(코드 값은 model-runtime이 정하고 계약 밖) 키 이름에 값이 실릴 수 있다. 그래서 0004와 같은 허용 목록·값 검증 방식으로 식별자 모양 키만 남긴다. 모양이 다른 키(한글, 소문자, `@` 등)는 버린다.
- 한계: 대문자 식별자 모양의 이름("JOHN")은 구별하지 못한다. 0004의 `code` 키와 같은 한계다. 키 모양과 길이 32는 근거 기록 없는 보수적 임의값이다. 실제 코드 집합(P*, G*)은 model-runtime의 것이라 이 영역은 확인하지 못했다.
- 대안: (a) 계속 비운다: 안전하나 분석 신호를 버린다. (b) 키 이름 허용 목록을 설정에 열거한다: 더 엄격하지만 model-runtime 코드가 바뀔 때마다 이 영역 설정을 고쳐야 한다. 코드 집합을 확인하면 이쪽으로 바꿀 수 있다. (c) 건수 합계만 남긴다: 규칙별 분석이 안 된다. (d) 모든 키 보존: 키가 값일 수 있어 버린다.
- 결과: 얻는 것은 규칙별 건수 분석. 감수하는 것은 위 한계와 정책 지문 변경(설정을 켜면 이전 정책으로 비식별한 사례와 지문이 다르다. 기존 사례는 재처리하지 않는다).
- 되돌리는 조건: model-runtime이 코드 집합을 계약에 확정하면 (b)로 바꾼다. 키에서 식별 사례가 나오면 설정에서 필드를 빼 비운다.
