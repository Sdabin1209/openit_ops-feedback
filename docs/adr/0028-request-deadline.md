# 0028. 사람용 요청에 서버 쪽 요청 전체 마감을 둔다

- 상태: 채택(U428, 헤드 결정 D120).
- 맥락: 게이트웨이는 검토 경로(읽기 3개·검토 게시)에 연결 1초 + 응답 머리글 10초를 준다. 이 서버의 최악은 DB 호출 하나만 봐도 11초(문장 상한 3+1, 재접속 상한 3, 다시 문장 상한 3+1, ADR 0008)이고 검토 게시는 호출이 여러 번이다. 서버는 계속 일하는데 화면은 504를 받는다(U427 보고).
- 결정: 사람용(게이트웨이를 지나는) 요청마다 **요청 전체 마감 9.0초**를 둔다(`wiring/ingest_service.REQUEST_DEADLINE_SECONDS`). 요청이 시작될 때 주입한 시계로 마감 시각을 정하고(`wiring/deadline.py`, 요청 범위 contextvar), 각 DB 호출(`PgBase._x`)은 남은 시간이 고정 상한(문장 상한+1초)보다 짧으면 남은 시간을 상한으로 쓰고, 남은 시간이 0 이하이면 시작하지 않는다. 검토 게시는 단계 사이(읽기 전, 조립 전, 쓰기 전)에도 마감을 본다. 넘기면 503 `UNAVAILABLE`(retryable=true)을 낸다.
- 왜: 마감 전파(deadline propagation, gRPC 마감과 같은 방식)가 시간 사슬(바깥 > 안쪽, D119)을 지키는 표준이다. 값 9.0 = 게이트웨이 상한(1+10초) 11초에서 여유 2초를 뺀 설계 값이며 측정하지 않았다. 컴포넌트와 저장소가 마감을 인자로 끌고 다니지 않도록 요청 범위 변수에 둔다(요청마다 따로).
- 되돌림·재시도 안전: 이 영역의 쓰기는 사례 게시 한 문장(자동 커밋 INSERT, 이미 있는 (case_id, version) 조건과 같은 검토 재전송의 200 멱등)뿐이고 마감은 그 문장 전에 확인한다. 쓰기 문장 도중에 소켓이 끊겨 불확실하면(ADR 0008의 재시도 근거) 같은 요청을 다시 보내도 한 번만 반영된다(`tests/test_request_deadline.py`).
- 검토한 대안: 마감을 두지 않고 DB 상한만 줄이기(호출이 여러 번이면 합이 여전히 길다), 환경 변수로 받기(계약 `OpsFeedbackServerEnv`가 이름을 정해야 한다: [CR-011](../change-requests/CR-011-request-deadline-env.md)).
- 결과: 얻는 것은 서버 최악 < 게이트웨이 response_header(`tests/test_exposure.py`가 설정 값으로 고정). 감수하는 것은 느린 DB에서 검토가 503으로 끝나 사람이 다시 눌러야 한다는 점.
- 되돌리는 조건: 게이트웨이 상한을 키우면(사슬을 다시 정하면) 이 값을 같이 올린다.
